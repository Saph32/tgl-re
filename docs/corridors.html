Where a corridor comes from

Entering corridor c ($51) loads three things. Its tileset: scene 1 and then scene $EF55[c] (bank 5, the same scene system the labyrinth uses — background tiles, eight metatile sets, palettes). Its music: $EF2A[c]. Its stage: $EF9B switches to bank 4 and calls its only entry, $8000, which returns the block address from the 25-entry table at $8013, indexed by c + 2. The block is an event stream, and it is the whole stage: nothing else in the ROM says what a corridor looks like or what attacks in it.

How a stage is decoded: one row at a time

  1. Scroll ($E530, every frame): the screen moves by the current speed $B8/$B9, in 1/256 pixel per frame; the whole pixels this frame land in $B7.
  2. Count pixels ($E69B): $AF adds them up, and every 16 pixels — one metatile row — it rolls over and the row counter $B0/$B1 goes up by one ($E6B3). The row counter is the stage's clock: every event is keyed to it.
  3. Fire events ($E6CE): while the row counter equals the pending trigger $B2/$B3, the next record's command runs (dispatched through $E6F3) and $E89D reads the trigger after it. Several records can share a row.
  4. Build the new row ($E8AB): 16 metatile ids from the background strip into $04C0, then each of the eight overlay slots writes its structure's next row over them.
  5. Draw it and spawn from it: bank 5 $83B3 draws the 16 metatiles (five bytes each) and writes each one's fifth byte back into $04C0; bank 5 $89FB then spawns a ground object for every cell whose fifth byte has a high nibble (below).
  6. Tick the waves: $E98F sets $A0 bit 2, which is what a corridor spawn script's waits count; $E655 clears it next frame.

The event stream

A block starts with a two-byte trigger (the row its first record fires on, normally 0). Every record is then [command][operands][next trigger lo][next trigger hi]: each record carries the row at which the record after it fires, so triggers never decrease within a block — one of the checks the parser relies on. Command 3 jumps (a block is a graph, not a list); the stream simply stops being read when the scroll stops, because the row counter stops.

The background: a repeating strip, with structures on top

The strip. A row table is [rows lo][rows hi][count]. $E8AB takes row $A1 — counting 0 to count−1 and round again — as 16 metatile ids at rows + 16 × $A1. So a corridor's floor is a short loop of rows (one to a handful), repeated for as long as the stage runs, and a command 1 can switch to another strip mid-stage. A metatile id is the labyrinth's: set (bits 5-7) and metatile (bits 0-4) in the scene's eight sets.
Overlays. Everything that is not floor — walls, buildings, craters, bridges — is a structure written over the strip by one of eight overlay slots ($0400-$045F, one byte per slot per field). Each new row, every active slot writes its structure's next row at its column; after the last row it can repeat, shifted sideways, and then goes idle (column $80).

A structure is [width][height] and then its rows, read by $E90F as codes: $00 n skips n columns (the floor shows through), $01 ends the row early, and any other byte is a metatile id written at the current column. A row is done once width ids have been written. A slot moving off either edge (column $20-$EF) is switched off.

Scroll speed

The current speed is $B8/$B9, a 16-bit number of 1/256 pixel per frame. Every frame $E66A moves it 2/256 towards the target $BA/$BB — so changes of speed are smooth ramps, 128 frames per pixel-per-frame — and only command 0 sets the target. With bit 7 of its high byte set, command 0 sets the current speed too, with no ramp. A speed of 0 (used four times, two of them at once) halts the scenery, and since rows then stop coming, so does the event stream. Rows arrive every 16 × 256 ÷ speed frames: at $0100, one pixel per frame, a row every 16 frames.

What makes enemies appear

  • Waves — command 2 with bit 1 starts a spawn script in bank 4, run by the same interpreter as the labyrinth's ($F78F): spawn a type, spawn a formation (a type-$29 spawner that releases count of a type every interval), wait, jump, end. In a corridor a wait counts rows, not frames: it only ticks when $A0 bit 2 says a new row came in — so waves stay pinned to the scenery whatever the speed. See Enemies for the scripts.
  • Ground objects — placed by the scenery itself. A metatile's fifth byte has a high nibble on cells that carry something; when $89FB sees one in the new row, it looks up that nibble in the spawn list of the metatile's set ($803C[the set's list number]) and spawns that object type at the cell's column. So whatever row or structure puts such a metatile on screen also places its object — no spawn script is involved.
  • Bosses — command 5 sets $70 = 1. Bank 3 $9184 then runs the boss phase: it spawns the boss type ($9151[corridor], or command 5's operand in corridor 21) and waits for it; the score counted for the TGL game's rewards is taken here, and the boss clock runs while it lives. Command 9 is the stream's only way to test $70.
  • The art they need — command 7 queues a graphics-load stream ($E99F decompresses its blocks into sprite CHR); an object whose block has not arrived yet waits ($CF5F).

Bank 4, decoded

Bank 4 is 100% claimed: the 25 event streams, and the data they point at — 13 row tables and 13 groups of background rows, 142 structures, 1 runs of inline overlay rows and 7 palette lists, 6,249 bytes — plus the bank's spawn scripts and graphics streams (tools/parse-enemies.py). CORRECTION: the data half was claimed as a lead with its contents not established; reading the handlers that consume it decodes all but 30 bytes, and every decoded piece lands inside it, none outside. Four pieces overlap on purpose (inline overlays pointing into rows) and are claimed as shared. What is left: an unused row table and its row, two unused 1 × 2 structures, one byte, a never-matching trigger, and the bank's closing fill.
Not established. What bit 0 of $60 does (command 2). How the overlay column maps to the screen when the playfield is wider than 16 metatiles. Nothing here has been checked against a savestate taken in a corridor beyond the tileset (CHR 141/142, sets 6/6) and Fleepa.
