Why this bank sits where it does

UxROM wires the last bank to $C000-$FFFF permanently, and this is the last of the eight. Confirmed rather than assumed: the three interrupt vectors in this bank's own tail point at $DC75, $FEDE and $DCF3, and all three addresses decode as sensible handlers when this bank's bytes are placed at $C000. The seven fixed-address bank-switch routines at $D714-$D76E and the generic one at $D705 are also here, as they must be - code that switches the $8000 window cannot be running in the $8000 window. The boot-time bank check at $FF23-$FF43 selects each of the other seven banks in turn and confirms it answers with its own number, so the reset path itself asserts that this bank stays put while the others move.

This is the fixed bank. UxROM wires the last PRG bank to $C000-$FFFF and there is no register that can move it, so these bytes are visible to the CPU at every moment the console is running. That is why the interrupt vectors, the bank-switching routines and the far-call trampoline are all here: none of them could work from a window that is about to be switched out from under them.

bank7.bank_table_FFF2 · file 0x20002-0x20009 · 8 bytes · PRG bank 7 · CPU $FFF2-$FFF9

Eight bytes, $80 through $87, one per PRG bank, at $FFF2-$FFF9. This is the standard UxROM answer to bus conflicts. On these boards a write to $8000-$FFFF is ANDed with whatever the ROM is driving at that address, so the only write that is guaranteed to land is one whose value already equals the ROM byte. The game therefore never writes a bank number out of thin air: it reads entry n of this table and writes the byte straight back where it came from, so the two agree by construction. The high bit is set in all eight values and is discarded - UxROM latches only as many low bits as it has banks, and with eight banks that is the low three - which is why $80+n selects bank n. Confirmed by the switching code and not by the shape of the table: $D79F-$D7A2 is LDA $FFF2,Y / STA $FFF2,Y with Y holding the bank number, $D70B-$D70E is the same pair, and seven more routines at $D719, $D726, $D733, $D740, $D74D, $D75A and $D767 do it with the address of one fixed entry. Both edges of the region are pinned by structure rather than argued: $FFF0-$FFF1 are $FF, and the byte after the eighth entry is the low half of the NMI vector. LEAD, not established: the eighth entry ($87, bank 7) exists, so the fixed bank can in principle also be selected into the $8000 window - but the seven fixed-address routines cover banks 0 to 6 only, and no call site has yet been found that hands the generic routine a 7.

6502 interrupt vectors vectors confirmed

bank7.vectors_FFFA · file 0x2000A-0x2000F · 6 bytes · PRG bank 7 · CPU $FFFA-$FFFF

The three 16-bit little-endian addresses the 6502 fetches on NMI, on reset and on IRQ/BRK. Their position is fixed by the CPU, not chosen: $FFFA, $FFFC and $FFFE are the last six bytes of the address space, which is why they are the last six bytes of the file. All three point into bank 7, which is the only place they could usefully point on a UxROM board - $C000-$FFFF is the one window that is guaranteed to hold the same bytes whatever the bank register says. Each target was disassembled and each decodes as the handler its vector names, which is the check that makes these six bytes a confirmed claim rather than a convention: a wrong pair here would still be a legal address, and only the code at the other end can say it is the right one.

$FFFA  75 DC DE FE F3 DC                                |u.....|
nmi
$FFFA · +0 · 2 bytes · 75DC · = 56437
NMI vector = $DC75, taken once per frame at the start of vblank. The target is a vblank handler and decodes as one: PHA / TXA / PHA / TYA / PHA saves the registers, then $FE is masked with #$E7 and written to PPUMASK, a frame counter at $2B is incremented, PPUSTATUS is read into $26, and OAM DMA is kicked off by writing $00 to OAMADDR and $02 to OAMDMA - so sprite memory is staged in CPU page 2. NOT YET ESTABLISHED: whether this handler ever dispatches through a vector held in RAM. The playbook warns that a RAM vector is where a static trace stalls and that it can hide a quarter of a bank, so that question has to be answered before any coverage figure for bank 7 means anything.
reset
$FFFC · +2 · 2 bytes · DEFE · = 65246
RESET vector = $FEDE, taken at power-on and on the console's reset button. The target is a textbook 6502 power-on sequence and decodes as one: SEI / CLD / LDX #$FF / TXS, then $30 to PPUCTRL, then PPUSTATUS polled until bit 7 clears three times over (the standard wait for the PPU to warm up), then $0F to APUSTATUS and $C0 to $4017, then a loop that clears all eight pages of $0000-$07FF with a single X index. The clear covers $0100-$01FF, so the stack is zeroed too - which is worth knowing before reading anything into stack contents in a savestate.
irq
$FFFE · +4 · 2 bytes · F3DC · = 56563
IRQ/BRK vector = $DCF3. This one is not a stub, and that is worth saying out loud because on many cartridges it is: mapper 2 has no scanline counter, so the only interrupt source on this board is the APU - the DMC sample-finished IRQ or the frame counter. The handler saves A, writes $0F to APUSTATUS, reads the frame counter at $2B, and then polls PPUSTATUS bit 6 (the sprite 0 hit flag) with BIT/BVS in a short loop before reloading DMC_FREQ from $05 and returning with RTI. So the same handler is doing sample housekeeping and mid-frame timing. NOT ESTABLISHED: which of the two interrupt sources is actually enabled, and when. That is a question about writes to $4010 and $4017 elsewhere in the ROM, and those have not been enumerated.
