Password

Thirty-two characters, six bits each, a running XOR key and a checksum — and a back door that skips all of it.

A character is stored as its position on the grid, not as a letter. $88F2 is LDX $17 / LDA $16 / STA $0411,X, and $16 holds the cursor's grid index. So A is 0, T is 19, 0 is 26, a is 30 and ? is 63 — 64 values, exactly six bits. The layout is read off the nametable of a savestate taken on the password screen; lowercase letters are tiles $81-$9A, drawn under a row of $AE dots, so on screen they carry an umlaut.
Correction. This page used to show a 36-character grid, A-Z and 0-9, with 4-9 at 30-35. The savestate had seven rows and only three were read; 4-9 are 56-61. It was a scanned manual, whose former owner wrote passwords full of umlauted letters, that prompted the second look (outside sources).

A blank and the letter A are the same byte. A's grid index is 0, and the savestate shows an untouched entry field is all $00. Nothing in the field distinguishes "not typed" from "typed an A". That matters below. This is what the code says; it was not tried on hardware.

How a password decodes

All of this is read off $8516 in bank 3, which is the bank the password screen runs with live — the savestate's mapper latch reads $83.

1. The seed comes out of the last two characters

seed = ((char[31] << 2) | (char[30] >> 4)) + $1D      ; $8519, kept in $19

So the two characters that look like the tail of the password are really its key. Change either one and every decoded byte changes.

2. Four characters become three bytes

$85BB copies four characters to $0403, masks each with AND #$3F and shifts them together. Six bits times four is twenty-four, which is three bytes exactly — and the character boundaries deliberately do not line up with the byte boundaries:

3. Every byte gets a different key

$854D:  EOR $19        ; XOR with the seed
        DEC $19        ; and the seed counts down

$854B:  CPX #$17 / BEQ ; ...except byte index $17, which is exempt

Eight groups of four characters give 24 bytes at $011E-$0135. That buffer is the PPU write queue's staging area, borrowed while the password screen is up. Why index $17 is exempt is not established.

4. The checksum decides

$859B:  sum of $011E..$0133, plus $0135
        CMP $0134
        BNE $8578      ; SEC / RTS  -> rejected
        ...            ; copy to $0438, CLC / RTS -> accepted

There is also a short circuit: $8552 counts how many decoded bytes already differ from $0439,X into $18, and if none do, $8576 returns carry clear without copying anything.

The back door

Three bytes at bank 3 $8513 read $13 $06 $0B, which as grid indices is TGL. $857C compares them against the first three characters, and $8589 then requires every character from index 3 to $1F to be zero. On a match $8592 sets $2F = 0 and $30 = 2 and returns carry clear — the checksum at $859B never runs. $30 is the game-mode byte.
$857A:  LDY #$00
$857C:  LDA $8513,Y      ; 13 06 0B
        CMP $0411,Y      ; the entry field
        BNE $859B        ; ...otherwise fall through to the checksum
        INY / CPY #$03 / BNE $857C
$8589:  LDA $0411,Y      ; and everything after must be blank
        BNE $859B
        INY / CPY #$20 / BNE $8589
        STA $2F          ; A is 0 here
        LDA #$02 / STA $30
        CLC / RTS        ; accepted
And the ROM names it. Bank 0 $8BA3 is a screen script reading “PASSWORD TGL”, sitting immediately after one reading “PRODUCED BY / IREM / CORPORATION”. Both parse cleanly under the screen-script format derived elsewhere in this project, on blocks that were not used to derive it. What the mode actually does is not established — only that the ROM contains a screen that says this.
Because a blank and an A are the same byte, “TGL” followed by any number of A’s is byte-identical to it followed by blanks, and $8589 cannot tell them apart.

Try it

The same arithmetic, transcribed into the page. Type a password and it decodes exactly as bank 3 would — including the back door, which is checked first here just as it is there.

Regions

PPU script at $8B67 data confirmed

bank0.ppuscript_8B67 · bank 0 $8B67-$8BA2 · 60 bytes

A screen-painting script for the renderer at bank 0 $8495, painting from PPU $2220: 5 items over 6 row breaks, 60 bytes, ending at $8BA2 on the $FE the renderer stops at. An item is [col][count][characters]; the column is ORed into the PPU address low byte, $FF ends a row and adds $20 to the address, and bit 7 of the count means repeat one character instead of advancing through the source, which is a run-length fill. THE ENDING CREDITS. $891B points $16/$17 at $89F9 once; each pass of the loop at $8927 renders the next script at PPU $2220 - $8495 leaves the pointer just past the $FE - waits $8BB2[$F0] seconds and clears the text. So this script is reached by SEQUENCE, not by any pointer: nothing in the ROM names its address. Screen 9 of the chain $89F9 (MISSION COMPLETE) ... $8BA3 (PASSWORD TGL), which partitions $89F9-$8BB1 exactly. The printable bytes read as: "CREATED BYCO"PILEPRODUCED BYIREMCORPORATION". "PASSWORD TGL" screen script text confirmed

bank0.text_8BA3 · bank 0 $8BA3-$8BB1 · 15 bytes

Fifteen bytes: col 2, count 12, 'PASSWORD TGL', then $FE. THIS IS THE BACK DOOR'S OWN SCREEN. The password routine in bank 3 has a special case for the three characters T, G and L (see bank3.data_8513), and this is the text that names it, sitting immediately after the IREM credits script. WHAT THE SCREEN DOES is not established - only that the ROM contains a script that says this. HOW IT IS REACHED (found later): it is the tenth and last screen of the ending-credits chain. The loop at bank 0 $8927 renders the scripts from $89F9 in sequence at PPU $2220; after the ninth (CREATED BY COMPILE / PRODUCED BY IREM CORPORATION) $899F waits for Start, then takes one more pass - the wait $8BB2[8] = $8BBA - and renders this one. So pressing Start at the end of the credits shows the back-door password. CORRECTION: the region bank0.text_8B80 ('PRODUCED BY / IREM / CORPORATION' as a script of its own) was wrong - $8B80 is the middle of the ninth screen's script, which begins at $8B67 with CREATED BY / COMPILE.

The TGL password constant data confirmed

bank3.data_8513 · bank 3 $8513-$8515 · 3 bytes

Three bytes, $13 $06 $0B. Those are grid indices, not ASCII: the password entry grid is A-Z then 0-9 read left to right and top to bottom, $88F2 stores a character as its grid index with LDA $16 / STA $0411,X, so A is 0 - and 19, 6, 11 is T, G, L. The on-screen grid in a password-screen savestate confirms the layout row by row. READ BY $857C: LDA $8513,Y / CMP $0411,Y for Y = 0,1,2, after which $8589 requires every character from index 3 to $1F to be zero. On a match $8592 sets $2F = 0 and $30 = 2 and returns with carry clear, SKIPPING THE CHECKSUM at $859B entirely. $30 is the game-mode byte. Bounded by its reader's operand and by the code either side: $8512 is an RTS and $8516 is a traced instruction start, so these three bytes are exactly the gap between. A CONSEQUENCE OF THE ENCODING, stated because the code says so and not because it was tried: a blank and the letter A are both the byte 0 - the savestate shows an untouched field is all $00 - so 'TGL' followed by any number of A's is the same 32 bytes as 'TGL' followed by blanks, and this check cannot tell them apart.

What the 24 bytes are. $85B0 copies buffer index i to $0439 + i, and bank 3 $8473 turns that into game state: indices 0-16 become $04A0-$04B0 — corridor flags, weapon levels, the Enemy Eraser count and the keys; index 17 the maximum life ($47, high five bits); 18 and 19 attack and shield; 20 and 21 the score; 22 is the checksum; 23 is read by nothing. $83AE runs the other way — the game’s own password generator.

The TGL game: corridors only

What $30 = 2 does. Bit 1 of $30 is tested wherever the game would go back to the labyrinth, and every time it sends the player to the next corridor instead — with a reward screen in between.

The loop. A new game ($EB18) clears $51 and $77 and starts corridor 0, the opening flight. When a corridor ends, $ECE7 tests $30 bit 1: in a normal game it returns to the labyrinth, in the TGL game it far-calls the reward screen (bank 3 $80A0), then $ECFC takes $51 = $ED08[$77], increments $77 and starts that corridor. After corridor 21 the normal ending runs. The HUD shows the corridor number instead of the area ($E169).

Corridor order, $ED08

1 → 11 → 12 → 2 → 13 → 3 → 14 → 4 → 15 → 5 → 16 → 6 → 17 → 7 → 18 → 8 → 19 → 9 → 20 → 10 → 21 — each of 1-21 exactly once (checked): the second-half corridor of a pair is played before the first of the next.

What the score buys, $817A

The score it counts is corridor score, less a boss clock. Each corridor start copies the score into $04B9 ($EF86); when the boss appears bank 3 $91A7 turns that into the points gained so far, and during the fight $9305 takes 10 points off every 64 frames, down to zero. The reward screen adds the result to a running total at $04B3 (bank 6 $805A) and prints it. $15 is that total in units of 10,000 points (capped at 255), and $80E7 hands out every entry from $76 onward whose threshold is at most $15 — through bank 2 $86BC, the ordinary pick-up routine. $76 persists, so each entry is given once per game; at most five fit on a screen (the loop stops at PPU row $23xx), and the rest wait for the next corridor.
