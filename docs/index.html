What is in the container

iNES header header confirmed

header.ines · file 0x00000-0x0000F · 16 bytes

The iNES container header. Bytes 8-15 are all zero, so this is a plain iNES file and not NES 2.0 (NES 2.0 puts the value 2 in bits 3-2 of byte 7; byte 7 here is $00). Unlike some dumps, nothing in this header has been found to disagree with the file: byte 4 declares 131072 bytes of PRG, byte 5 declares no CHR, and 16 + 131072 + 0 = 131088 is exactly the size of the file. Bytes 6 and 7 together encode mapper 2. tools/tgl/model.py re-derives the mapper number, the PRG figure and the zero CHR figure from these bytes on every build, so none of the three can drift away from what is written here.

magic
+0 · 4 bytes · 4E45531A
The constant "NES" followed by MS-DOS end-of-file ($1A). Identifies the file as iNES.
prg_rom_size
+4 · 1 byte · 08 · = 8
PRG ROM size in 16 KB units: 8 x 16384 = 131072 bytes. The unit is a property of the container rather than of the mapper, but here it happens to match UxROM's own 16 KB PRG banking exactly, so this ROM has 8 banks of 16 KB and the container's units and the mapper's units are the same thing.
chr_rom_size
+5 · 1 byte · 00 · = 0
CHR ROM size in 8 KB units: zero, so there is no CHR ROM in this file and the board carries CHR RAM instead. This is the single most consequential byte in the header for this project. It means no tile data is present in the file as tiles; every tile the PPU ever draws was written into RAM at runtime by code reading PRG, so finding the uploaders is the whole graphics problem here. The file size confirms the zero independently: 16 + 131072 leaves nothing over.
flags6
+6 · 1 byte · 21 · = 33
$21 = 0010_0001. Bit 0 (mirroring) = 1, vertical; bit 1 (battery-backed PRG RAM) = 0; bit 2 (512-byte trainer) = 0, so PRG begins at file offset 16; bit 3 (four-screen VRAM) = 0. Bits 7-4 = 0010 are the low nibble of the mapper number. The mirroring bit is the operative one on this cartridge, unlike on an MMC1 board: mapper 2 has no mirroring register, so the arrangement is wired and cannot change during play.
flags7
+7 · 1 byte · 00 · = 0
$00. Bit 0 (VS Unisystem) = 0; bit 1 (PlayChoice-10) = 0; bits 3-2 = 00, so this is iNES and not NES 2.0. Bits 7-4 = 0000 are the high nibble of the mapper number, giving mapper $02 = 2 = UxROM.
prg_ram_size
+8 · 1 byte · 00 · = 0
PRG RAM size in 8 KB units. Zero, which by the iNES convention is read as 8 KB for compatibility rather than as none - and which flags6 bit 1 says is not battery-backed in any case. Whether this board populates work RAM at $6000-$7FFF has NOT been established from the ROM: no code has yet been traced that reads or writes that range.
padding
+9 · 7 bytes · 00000000000000
Bytes 9-15, all zero. In the original specification byte 9 is a TV-system flag and bytes 10-15 are reserved; all-zero here means NTSC and nothing else claimed. All seven being zero is also what rules out NES 2.0 and what rules out the handful of dumping tools that wrote their own name into this space.

How the cartridge is wired

Mapper 2 — UxROM

Mapper 2. A single write to any address in $8000-$FFFF loads the PRG bank register, which selects which 16 KB bank appears at $8000-$BFFF. The last bank - bank 7 here - is hard-wired at $C000-$FFFF and cannot be switched out, which is why the interrupt vectors and the switching code itself live there. There is no CHR banking, no scanline IRQ and no mapper-controlled mirroring: the board wires mirroring fixed, and iNES byte 6 bit 0 says vertical.

Bus conflicts, and how this ROM avoids them

UxROM boards put the latch on the same bus as the ROM, so a write to $8000-$FFFF is ANDed with whatever the ROM already holds at that address unless the two agree. This ROM avoids that in the textbook way: it keeps a table of the eight bank values at $FFF2-$FFF9 and switches by reading a byte from the table and writing it straight back to the address it came from, so the written value and the ROM value are the same byte by construction.

Evidence. $D79F-$D7A2 is LDA $FFF2,Y / STA $FFF2,Y, and $D70B-$D70E is the same pair. Seven more sites do it with a fixed address instead of an index - $D719/$D71C for bank 0, then $D726, $D733, $D740, $D74D, $D75A, $D767 for banks 1 to 6, each preceded by LDA #n / STA $04. A byte scan of the PRG for the three store opcodes based at $FFF2 (8D/9D/99) finds no other site.

Mirroring — vertical

iNES byte 6 bit 0 is 1, which the specification reads as vertical mirroring. Mapper 2 has no mirroring control register, so unlike the MMC1 cartridges this toolchain came from, this cannot change at runtime and the header's bit is the whole answer. NOT CHECKED: whether the game ever relies on that arrangement in a way the ROM would show.

CHR RAM

iNES byte 5 is $00. By the iNES convention that means the cartridge has no CHR ROM and the board carries 8 KB of CHR RAM instead, which the file confirms by its size: header + PRG accounts for every one of the 131,088 bytes. NOT YET ESTABLISHED from the ROM: which code uploads the tiles. Per the playbook that is the whole graphics problem on a CHR RAM cartridge, and no uploader has been traced yet. The 8192 figure is the standard size for the board and is NOT derived from anything in this file.

Interrupt vectors

NMI$FFFA$DC75
RESET$FFFC$FEDE
IRQ/BRK$FFFE$DCF3

$DC75, $FEDE and $DCF3, all in bank 7 - which is the only place they could usefully be, since bank 7 is the one the CPU can always see. All three were disassembled and all three decode as the code their name implies: RESET is a textbook power-on sequence (SEI/CLD/LDX #$FF/TXS, then three PPUSTATUS polls, then a clear of $0000-$07FF), NMI saves A/X/Y and runs a vblank handler that does OAM DMA from page 2, and IRQ is a real handler rather than a bare RTI - it polls PPUSTATUS bit 6 and reloads DMC_FREQ. See the vectors region for the byte-level argument.

The bytes themselves, and the argument for each target, are on bank 7.

The eight PRG banks

A PRG byte has a CPU address only once you say which bank it is in. Banks 0 to 6 are all selected into the same $8000-$BFFF window, so an address there names seven different bytes; bank 7 is wired to $C000-$FFFF and is the only one an address identifies on its own.

Open threads

What is not established, kept here rather than in anyone's head. Each of these is a claim about the searches run so far.

  • THE GRAPHICS, part done. The font is decoded and confirmed against a savestate - 45 glyphs, 1bpp, seven bytes each, bank 2 $8BF8, expanded by $806C. The BULK tile data is still not found; the savestate diff says 12.8% of live CHR appears verbatim in the ROM in codec-shaped literal runs. Next: find the decompressor, and take a second savestate from inside a stage.
  • Bank 4 is explained but still barely traced. It is 25 per-area screen-data blocks behind a pointer table at $8013, indexed by the area number in $51, and its single entry point returns a pointer rather than running code - which is why a control-flow trace found 19 bytes of it. The blocks are a command stream walked through ($BC) and dispatched by the 10-entry table at $E6F3, now resolved. Parsing the command stream would claim most of the bank; none of the ten handlers has been read yet.
  • RESOLVED, and stated here because the correction matters more than the finding: the two inline PPU-string routines were carried for a while as variable-length streams whose termination could not be established, on the reading that $D57C-$D584 loops over a run of items. It loops over ONE item, waiting for room - $D7C3 never touches $16/$17, so re-entering re-tests the same bytes. The block length is (first byte & $7F) + 3 for $D576 and two fewer for $D53F, and all 32 blocks the trace now reaches resume on a legal opcode. See annotations/dispatch.json and docs/text.html.
  • The game's text is decoded in all three of its formats: 32 inline PPU strings in the instruction stream, 20 dialogue messages behind a 21-entry pointer table at bank 5 $960F, and 3 screen scripts read by the renderer at bank 0 $8495. 3,056 bytes. docs/text.html lists all of it. The punctuation glyphs are read from context in every case and NONE can be settled from this ROM: a font would settle them and CHR is RAM, so no byte of the file is a tile until code uploads one.
  • A wording question raised from outside and settled against the bytes. A longer rendering of the corridor message was put to this project - 'THIS IS A MESSAGE SENT BY THE PREDECESSOR WHO INFILTRATED NAJU BEFORE YOU', 'MY HOME PLANET STAR NAU', 'I ESCAPED FROM NAU'. Its first and last paragraphs match this ROM's message almost verbatim; the middle does not. The words PREDECESSOR, INFILTRAT, ESCAPED, NAU, SEALS, OPERATIONS and MESSAGE SENT do not occur in this file in any case, under any of the 256 additive keys, any of the 256 XOR keys, bit reversal or nibble swapping. The only prose in the ROM is the bank 5 block. So the quoted wording is from a different source or revision, not something this search has failed to find - and that negative is a claim about exactly those searches.
  • What bit 7 of a PPU-string count byte means. Two sites use it - bank 0 $845F and $8469, both writing ':' and two spaces to PPU $2286 - and it is masked off before the length is computed, so the queue's consumer is what sees it.
  • The $C0-and-above form of a PPU-string item, whose length is a fixed 9 rather than a character count. Two sites, bank 5 $86DD and $86EE, and neither payload is ASCII.
  • 26 reached routines never return - no RTS is reachable in any of them. That is computed by trace-code.py rather than listed, and it is what stops the walk at 5 call sites. The one that mattered: bank 2 $8AFF far-calls bank 0 $8015, an endless display loop, and the bytes after it are the block the pointer built at $8AC8/$8ACC names.
  • The three inline jump tables are read at one entry each, and that entry is never statically known, so in practice none is read at all: $9F2F and $A1C1 in bank 5 and $E6F0 in bank 7 all arrive with the index in A at runtime. Resolving them by hand into dispatch.json and seeding every entry is the next unlock after the strings. At $E6F0 ten plausible addresses follow the call, all $E7xx/$E8xx - but ten is where they stop at that one site and is not a claim about the others.
  • Bank 4 is reached at 20 bytes of 16,384. Its opening JMP table has a single entry, no far call in the ROM targets it, and no bank switch to 4 has been reached. Per playbook section 12, a bank that stalls this hard is one unenumerated mechanism, not a thousand separate problems.
  • JMP ($10C0) at bank 2 $8A97 is a jump through a RAM vector - $10C0 mirrors $00C0 in the 2 KB of CPU RAM. Nothing that installs it has been looked for. Playbook section 4 records this exact mechanism hiding a quarter of a bank on another cartridge.
  • The trace assumes a JSR returns with the live bank unchanged. 51 reached routines switch the bank in their own bodies and 89 call sites enter one; the list is computed by trace-code.py --risky and is untested rather than wrong, because a routine that switches and switches back is indistinguishable from one that does not without dataflow the tool does not do.
  • No latch write outside the nine switch routines is modelled. On UxROM any store into $8000-$FFFF loads the bank register, so a stray STA $8000 would switch banks. The check is an instruction-walk inventory of absolute stores over traced code; a byte scan is useless, as one run here confirmed by returning 1,331 distinct targets, nearly all operand bytes decoded as store opcodes.
  • CHR is RAM, so no tile exists in this file as a tile. No uploader has been found yet and no graphics region has been claimed. The cheap first question is not what points at a block but what routines write to $2007.
  • No reassembly check exists. Until one does, no claim about a region's extent has been machine-verified beyond its SHA-1 - and a SHA-1 says the bytes are the ones the writer meant, not that the boundaries are right. Build it before believing anything about extents.
  • The $FF runs at the end of each bank (37, 48, 16, 40, 14, 13, 46 bytes in banks 0-6 and 14 bytes at $FFE4 in bank 7) look like fill but are not claimed, because nothing has been checked about them beyond their byte value.
  • No RAM map exists yet. $04, $05, $10-$19, $21, $26, $2B, $2F, $30, $51, $54, $58-$5B, $76, $A5, $E4, $FC and $FE are all named by code read so far and have nowhere to be written down.
  • The routine the boot bank check calls on failure, $DED2, and the byte it stores at $0180, are not read - so what the seven failure codes at $FF3A mean is still open.

How to read these pages

Every region carries a confidence: confirmed means the claim was checked against the bytes or against code that executes; lead means it is a hypothesis worth recording and nothing more. Every region also declares the SHA-1 of its own bytes, and the build refuses to run if a hash stops matching, if two regions overlap, or if a region straddles a bank boundary. The machine-readable form of everything here is rom.json.
