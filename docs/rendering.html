Rendering

How the picture is made and how it scrolls: the cartridge's mirroring, what the NMI does every frame, the sprite-0 split that parks the HUD at the bottom of the screen, the corridors' vertical scroll and the labyrinth's room-to-room scroll.

In short. Mirroring is vertical, fixed by the board, so the two real nametables sit side by side ($2000, $2400) and $2800 and $2C00 are copies of them. Every frame is cut in two at scanline 192: above it the playfield is drawn with whatever scroll the game wants; at a sprite-0 hit the game rewrites the PPU address so that below it the HUD is drawn from the bottom of nametable 1, unscrolled. The playfield is 256 × 192; a corridor scrolls it vertically through nametable 0 and redraws one 16-pixel row ahead of it; the labyrinth keeps one room in nametable 0 and scrolls to the next with both tables.

Mirroring

iNES byte 6 is $21: bit 0 is 1, so vertical mirroring. Mapper 2 has no mirroring register, so this never changes. It means $2000 and $2800 are one table (NT0) and $2400 and $2C00 the other (NT1): two 32 × 30 tables side by side, each repeated below.

PPU addressTableHow the game uses it
$2000-$23FFNT0The playfield: the corridor (all of it), the labyrinth's room at rest, and one of the two rooms during a scroll.
$2400-$27FFNT1The HUD in rows 24-29, always; the neighbouring room during a horizontal scroll; the status screen.
$2800-$2BFFNT0 againWritten to, on purpose (see below).
$2C00-$2FFFNT1 againNever used.

The game relies on it, in two ways (the note in rom.json said this was not checked):

  • Horizontal scrolling needs two tables side by side. The labyrinth's east and west scrolls ($A8 counting 0–252 with the table bit $A9) run across the join between $2000 and $2400. With horizontal mirroring those would be one table over another and the scroll would wrap onto itself.
  • The $2800 alias. The corridor engine thinks of its world as two stacked screens: $AB flips each time the row counter wraps ($E98F-area code, bank 7 $EACC/$E6B9), and while it is 1 the row address is moved up by $0800. With vertical mirroring $2800 is NT0, so the same 30 rows are simply reused. Counted on the NES model over 120 corridor frames: 768 PPU writes to $2000-$23FF, 216 to $2800-$2BFF, 62 to $2400-$27FF (the HUD); over the labyrinth's north scroll, 864 to $2800-$2BFF, and none there for the east scroll. The scroll code toggles the vertical table bit $A7 the same way, which is invisible for the same reason.

The registers and the NMI

The game never writes the PPU's scroll or control registers from game code. It keeps shadow values and one routine copies them at the end of every NMI. Bank 7 $DC75, in order:

  1. Render off: $FE &= $E7 then $2001.
  2. Count the frame ($2B), read $2002 into $26, sprite DMA from $0200.
  3. $4015 = $1F: starts the DMC timer that will raise the split's IRQ (below).
  4. $DD54: the PPU writes — first one pending background row (the scroll engine's, below), then the generic queue at $0100 (a run of tiles, increment 1 or 32, or an attribute edit); and $DEC9: the palette shadow $0180 to $3F00/$3F10 when $017F is non-zero.
  5. If $30 bit 4 is set (a scrolling stage), write tile $FE into column 0 of the row under scanline 192 — the split's target (below).
  6. $D68B: $2000 = $FF, $2005 = $FD (horizontal), $2005 = $FC (vertical).
  7. Render on: $FE = ($FE & $E7) | $A3 — $A3 is 0 while the screen is blanked (fades, loading) and $18 otherwise.
  8. Sound tick (bank 0 $8009), then the random state is stirred.

The split screen

The status bar is part of the same frame, not a separate layer. The frame is 192 scan lines of playfield and 48 lines of HUD.

  1. Sprite 0 is a marker. OAM entry 0 is set by bank 7 $D51E to y = $BF (191), tile $FF, attributes $20 (behind the background), x = 0. With 8 × 16 sprites that is tiles $FE and $FF of the second pattern table; $FE's high plane is all ones, so it is a solid block. It sits in scan lines 192 and down.
  2. The background gives it something to hit. A solid background tile $FE in column 0 at scan line 192. In the labyrinth that tile is part of the room: the blank row written after the 12 room rows (bank 7 $F03D, $16 = $C0) starts with $FE, row 24 of the table. In a corridor the picture scrolls, so the NMI rewrites the marker every frame at the row that is under line 192 for the current $FC ($DCA2-$DCD2); the ones it leaves behind scroll away out of sight below the window.
  3. The split. When sprite 0 hits ($2002 bit 6, at line 192, because the top half of the sprite is solid), bank 7 $DD21 runs: $2006 ← $27, $00 (the PPU address becomes nametable 1, tile row 24, column 0, fine y 2, immediately), $2000 ← $FF with the nametable bits forced to 1, $2001 with the sprite bit cleared, and $2005 ← 0, 0 (which also clears fine x). The rest of the frame is NT1 from row 24: the HUD, unscrolled, with no sprites. The next NMI puts everything back.
  4. The HUD is NT1 rows 24-29 (the 192 ÷ 8 = 24 rows above it are the playfield): row 24 blank, 25 "SC … CHIP … SHOT", 26 the life meter, 27 "AREA … X … Y", then two blank rows. Row 24 being blank is why a couple of lines of timing slack at the join cost nothing.

Who does the split

Two routines can, and either may: the main thread waits for the hit in its frame-sync routine ($DA9A, the BIT $2002 / BVC loop at $DAB6) and calls $DD21; and the DMC interrupt (IRQ vector $DCF3) does it from the middle of the game logic. The IRQ exists because the main thread is usually busy, and this board has no scanline counter. The DMC channel is only a timer: bank 6 $802A loads a 17-byte all-zero sample ($4012 = $FF → $FFC0, $4013 = 1, $4010 with the IRQ bit set), and the NMI restarts it each frame ($4015 = $1F). It ends after 17 × 8 = 136 sample periods, and the IRQ handler acknowledges it ($4015 = $0F), spins on $2002 until the hit (giving up if the frame counter moves) and runs $DD21.

Tuning. The rate index in $05 (low nibble of $4010) is walked up one step whenever the IRQ turns out to be late (the hit has already happened, $DD15) and capped at $89. The periods below are the NTSC DMC table, which is outside knowledge, not in the ROM; the frame starts 2,273 cycles of vblank before line 0 and the hit is at line 192.

So it starts at $87 (set by $EDE8, late), is walked to $89 and stays: the IRQ arrives about 21 lines early and waits. That is the arithmetic of the table, not a run: the NES model delivers no IRQ, so in every run here the main-thread path did the split.

Corridors: vertical scrolling

A corridor does not scroll sideways ($A8 stayed 0 in the run; a stage is 16 metatiles = 256 pixels wide). Its picture lives only in NT0: 30 tile rows = 15 metatile rows = 240 lines, of which 192 show.

  • Speed. $B8/$B9 is the speed in 1/256 pixel a frame ($0180 = 1.5 in the run), moved 2/256 a frame toward the target $BA/$BB that the stage's commands set. Bank 7 $E530 subtracts it from $B6/$A6: $A6 counts down, so the picture moves down the screen and new rows appear at the top; when it passes 0 it wraps to 239 (sbc #$0F on the borrow) and $A7 toggles.
  • A row every 16 pixels. $AF adds the pixels moved; at 16 ($E69B) the next row is built ($E8AB: 16 metatile ids, then bank 5 $83B3 turns them into 32 + 32 tiles and 8 attribute bytes in $0130, $0150 and $04E8) and the row counter $B0/$B1 (the stage clock) goes up. $AE counts the 15 rows down, 14 to 0 and round again; $EACC turns it into the PPU address $2000 + $40 × $AE in $AC/$AD (plus $0800 while $AB is 1) and the attribute address in $AA.
  • Two NMIs per row. $A5 is the hand-off: 1 makes the next NMI write the attribute bytes and the first tile row, 2 makes the one after write the second tile row ($DD54). Ground objects created from the row take its PPU address with them (bank 5 $8A42: $AC/$AD into the object's own $05C0/$05D8), which is how a cannon patches its own background tiles later.
  • Where the new rows go. Not onto the visible rows: into the hidden 48 lines the window does not show. Measured: the row being written is 4 to 6 tile rows above the top of the window (for example row pair 2-3 while the window starts at row 7.75), so a row is written about three metatile rows before it scrolls into view.
  • The HUD is NT1 rows 24-29 and the marker is rewritten every frame (above), so the marker row runs ((192 + $A6) mod 240) / 8.

A corridor frame: NT0 (left) full of stage, NT1 (right) empty but for the HUD in its bottom rows (green); the red outline is the 192 lines on screen; the yellow marks are the $FE tiles in column 0 (the live one and the trail below the window). The right-hand picture is the NES model's frame; the coloured block at its lower left is sprite 0, which the model does not switch off at the split as the real PPU does.

The labyrinth: one room at a time

A room is 16 × 12 metatiles = 256 × 192, exactly the playfield, so at rest $A6, $A8, $A7 and $A9 are all 0 and the room is in NT0 rows 0-23. Bank 7 $F03D draws it a row at a time (two tile rows a frame, 13 frames), then one blank row with the marker. Everything that edits the room later (the blocks shots break, Shooting the room) writes to NT0 at the room's own position, so the room has to be in NT0 when it stops.

Moving to a neighbouring room is a scroll of exactly one screen ($A4 is the exit: 0 north, 2 west, 6 east, 8 south; $F09A chooses the routine). Measured on the NES model from the savestate, with the real game code running:

Putting the room back in NT0

When the scroll ends the new room is on screen but not where later code expects it, so it is re-homed without a visible jump, with the display switched between identical pictures. After an east or west scroll the new room is the whole of NT1 ($A9 = 1, $A8 = 0), so it is simply copied into NT0 (13 frames, hidden) and $A9 goes back to 0. After a north or south scroll the new room straddles the wrap of NT0, so it is first drawn whole into NT1 (13 frames), the display flips to NT1 at scroll (0, 0), it is drawn whole into NT0, and the display flips back. Run on the model, east exit: NT1 filled up to frame 32, the scroll 33-95, at 96 $A8 wraps to 0 and $A9 = 1, NT0 filled 97-109, $A9 = 0 at 112. West: NT1 filled to frame 27, scroll 28-94, NT0 filled 95-106, $A9 = 0 at 107. North: scroll to frame 73, NT1 filled 75-85, $A9 = 1 at 87, NT0 filled 88-100. South: the same shape. Then the cell map is rebuilt ($8006) and the ship placed ($F269).

At rest (first), half-way north (second: the window, in red, has wrapped round the bottom of NT0; the old room is the upper part of NT0, the new one is being drawn below it) and half-way east (third: the window straddles NT0 and NT1). The status screen

Select opens it (bank 7 $E4EE; bank 5 $84CB). It needs no split: it sets $A2 = 1 and $FC = $B4 (180) and draws its map, icons and text into NT1. Scrolling NT1 down by 180 lines puts its last 7.5 rows — the HUD — at the top of the screen and rows 0-17 below, so the HUD stays visible over the new screen with nothing to switch. Sprite 0 is not used ($30 bit 4 is clear). The room is in NT0 the whole time, untouched.
