Game loop

What happens in one 1/60 second of a corridor, and then of the labyrinth: the order of the work, how long it takes, what the NMI does behind it, and what only happens every so many frames. Jump to the labyrinth.

In short. The game is one loop with a frame sync in the middle of it, plus an NMI that interrupts the sync. Per frame: the NMI puts last frame's sprites, the scroll and one background row on the screen and ticks the sound; the loop then reads the pads, runs every object's handler (which moves, draws and collides it), steps the HUD, the decompressor and the boss state, scrolls the stage and runs the spawn script, and finally waits — for sprite 0, to cut the screen in two, and then for the next NMI. On the NES model a calm corridor's logic takes about 8,100 of the 29,781 cycles in a frame (27%), busy ones 10,000 to 18,000, and a boss fight 28,800 (97%), where the loop no longer has time to wait and the game runs at 56 iterations a second. The measurements.

The loop

Bank 7 $FF5D sets the game up and then spins in $FF7A:

FF7A  JSR $E655        ; the stage step: speed, scroll, new row, stream records
      LDY #$01
      JSR $FF8B        ; one pass of the frame body (below)
      JSR $D76F        ; far call: bank 3 $800F -> $917F, the stage/boss routine
      JMP $FF7A

FF8B  ...
FF8D  JSR $DA9A        ; FRAME SYNC: wait for sprite 0 (split), then for the NMI
      JSR $F493        ; read the pads; pause / status screen
      JSR $D76F        ; far call: bank 6 $8000 -> $81FB, the object loop
      JSR $E0F9        ; HUD meter, frame counter, score
      JSR $DB52        ; tile decompressor
      DEY / BNE $FF8D  ; Y passes

The listing starts at the top of the loop, but a frame starts in the middle: the NMI arrives while the main thread is waiting in $DA9A, and that is where the pads, the objects, the HUD and the decompressor run, followed by the boss routine, the stage step and the loader, and then the wait again. FF8B with Y = n (reached through $C024) is the call that runs the game for n frames, with pads, objects, HUD and decompressor all still going: bank 0's GAME OVER loop uses it with Y = 1. $FFD1 is the lighter wait that only syncs, which the labyrinth's room scrolls use.

  • Late frame: the NMI arrived while the logic was still running. The loop was not at its sync, so that NMI had only the previous iteration's sprites, scroll and row to put on the screen: the picture repeats and then jumps. When the loop reaches the sync with the NMI already counted ($2B non-zero) $DA9A skips both waits and the next iteration starts at once, short, so the game's own speed holds while the picture is irregular (the first four states keep 59.9 iterations a second).
  • The loop falls behind only when the logic takes most of a frame all the time: in more4 the object loop alone is about 26,500 cycles, the logic with a new row up to 36,660, and 52 of 900 frames pass without an iteration finishing: 56.5 a second, about 6% slower than the screen.
  • The split. When the logic runs past scan line 192 the main thread cannot do the HUD split in its sync, and that is what the DMC interrupt is for (it ran the split from the middle of the logic on the console). The NES model has no IRQ, so the 'missed' column counts frames in which the model would have left the HUD unsplit: a measure of how often the IRQ does the job, not of lost frames.

The NMI: what reaches the screen

Everything the loop computes is invisible until the next NMI copies it. In order ($DC75; also Rendering): rendering off; frame counter $2B up; sprite DMA; DMC restart; $DD54, which writes the one pending background row ($A5 says whether its first tile row, second tile row or neither goes this frame) and then the PPU queue at $0100; the palette upload; the sprite-0 marker; the scroll registers; rendering on; the sound tick (bank 0 $917C); and a stir of the random state ($2A is mixed with the stack pointer at that moment, which is as unpredictable as the instruction the NMI landed on). The NMI's own length varies (1,555 to 4,595 cycles over the five states, median about 2,100-2,300): the sound tick alone is about 1,600, and a long queue or a row adds to it. Rendering is off while the NMI runs (step 1 above), so whatever runs past the end of vblank (2,273 cycles in the model; the 513 cycles of sprite DMA, which the model does not count, would come on top) blanks the top scan lines of that frame. In the model that is 29-53% of frames (262 to 478 of 900), by up to 15 lines in the calm corridor and 20 in more3. This is arithmetic from the NMI's length, not something seen on a screen.

Consequence: one frame of latency. Sprites built in step 2 are DMA'd at the next NMI and the scroll registers set in step 6 are written then too, so a background that moved this frame and the sprites that moved with it (ground objects are shifted by the same $B7 the scroll step used) appear together, one frame after the logic.

The frame sync

$DA9A is two waits in one. If the NMI has already happened ($2B is non-zero) it just clears the flag and returns. Otherwise, unless the I flag is set (the IRQ already did it): with sprites enabled it spins on $2002 bit 6 ($DAB6) — first making sure the flag is not left over from the last frame — until sprite 0 hits at scan line 192, runs the split ($DD21), adjusts the DMC timer's rate, and then waits for $2B to become non-zero, i.e. the NMI. So the spin ends at cycle 24,227 and the rest, about 5,500 cycles, is a quiet wait. The DMC interrupt can perform the split earlier from the middle of the logic; on the NES model, which has no IRQ, the sync always did.

Reading the pads

$D64C reads both pads with ROL (A ends in bit 7, Right in bit 0) again and again until two consecutive reads agree, then keeps $F7/$F8 (held) and $F5/$F6 (pressed this frame). That is what a program has to do when the DMC channel is running, as this one's timer is. Then $F493 checks the pause and status keys ($E4B3): a new Start waits in a loop (the objects do not run, the sound does); a new Select runs the status screen. The player's own handler turns the D-pad into $32, a 3 × 3 cell index, each frame ($DAE1, which in a demo overwrites the pads with its own patterns first).

The object loop

Bank 6 $81FB. There are 24 object slots (Enemies): 0-4 the player and its shots, 5-23 everything else.

  1. Reset the sprite allocator ($CDB4: the first OAM entry to fill, $80, is normally entry 1 — entry 0 is the split's sprite 0).
  2. For each slot in turn ($35) whose type $0500+slot is not 0, jump through the split dispatch table ($80DE/$815D) to that type's handler; it returns to $8227. The order flips every two frames: slots 0-4 always come first, then 5→23 for two frames, then 23→5 for two (the table at $81DD, chosen by bit 1 of the loop counter $36). Measured: [0, 5, 6, 7, 8, 9, 23], [0, 23, 9, 8, 7, 6, 5], the same again, then forward again. Its effect is that when sprites run out, the ones that lose are not always the same ones.
  3. Finish ($CE88): sprites left over from the previous frame are hidden (y = $F8). Correction: this entry said the allocator's flag byte $83 is flipped every frame. It is flipped ($CEFE, bit 0 = the fill direction: upward from OAM offset 4, or downward from $FC) only when the frame ran out of OAM (bit 7) or when the PPU's sprite-overflow flag ($26 bit 5) was set. Run: in the calm corridor $83 stays $04 and the direction never changes; in the boss fight (63-64 sprites) it flips every frame ($84-$87) and the downward extent $81 steps $FC, $F4, $F0, $EC. So the sprites that lose when a line holds more than 8 alternate only when that actually happens.
  4. The player's death is decided here: the player's slot becomes the death object type 4 when a hit empties the life meter, and at the end of the loop, if the meter and $2E are all 0, the game goes to bank 0 $81DD (GAME OVER) (see the cell page).

What a handler does varies by type (a hundred and twenty-seven of them), but nearly all follow one shape, and every step is a call into a shared routine in bank 7:

  1. First frame: bit 7 of the type is clear, so initialise: hit points, attack, collision flags and drawing flags are copied from the per-type tables ($D02C, $D0AB, $D12A, $D1A9; $CFA0), the type gets bit 7.
  2. Move: a velocity, a spring toward a target ($CD12/$CD46), an aim at the player ($F863) or a script; ground objects also add the scroll step $B7 so they stay on the background.
  3. Draw: $CBE8 → $CC34 turns the object's metasprite id into hardware sprites in OAM at the allocator's cursor, one per pass of $CDD7, flipping and offsetting as the id says, from the position $0518 (y), $0530 (x).
  4. Hit box: $D229 makes a box from the position and the metasprite's half width and height ($C174, $C201).
  5. Collide: an enemy tests its box against slots 4 down to 0 ($D348) — a shot or the ship counts only if its collision flags share a bit with the test's mask — and $D2BB/$D2C5/$D39B then take each side's attack from the other's hit points. The player's own overlap with enemies and their shots is therefore found in the enemies' handlers, up to five box tests per enemy per frame.
  6. Die: at 0 hit points the type becomes $D441[type] — an explosion ($08, which is where the item box counter runs), a bigger one ($07) for bosses — and the handler for that type runs from the next frame.

The player (slot 0)

Bank 3 $8C98, once per frame: build $32 from the pad; in a corridor, steer: the ship's bank angle $0680 (0-10) moves one step toward the D-pad's left or right and picks the sprite and flip ($8EFD/$8F08); the direction becomes a velocity ($F8CE) and the position is clamped to x 12-244, y 24-176; B counts $33 down and spawns a bullet (the gun); A spawns a weapon object (the weapons); after a hit the ship spins for 15 frames and blinks ($0788, collision flags bits 7 and 6); the exhaust is drawn as a second piece whose frame follows the scroll speed.

Stage, boss, scroll and spawns

  • Boss and stage state (bank 3 $917F, after the decompressor): $70 is 0 for nearly the whole stage and the routine returns at once. A stream record sets it to 1 at the boss's row: 1 turns the score into the stage's points gained, plays the warning ($0300 = $40, sound $45) and, when the corridor's flags ($913A) say so, blows up the ordinary enemies; 2 waits ($73/$74, in 64-frame ticks, beeping) and starts the boss music; 3 creates the boss object ($72) and remembers its slot; 4 watches it (every 64th frame, $41 & $3F, the bonus ticks 10 down); 5/6 run the eight explosions, the victory song and set the stage-end flag $A0 bit 0, which $E655 sees on the next pass (Ending).
  • Stage step ($E655): clears the step $B7 and the new-row flag ($A0 bit 2); if the stage-end flag is up, hands over to $EB18; otherwise ramps the speed $B8/$B9 by 2/256 toward $BA/$BB, subtracts it from the scroll ($E530) and adds the whole pixels to $AF.
  • Every 16 pixels ($AF ≥ 16): finish the previous row's PPU writes ($E5EB), count the row ($B0/$B1, the stage clock), find its PPU address ($EACC), switch to bank 4 and fire every stream record whose trigger equals the row ($E6CE; speed changes, palettes, art loads, a wave script, the boss, the end), then build the row's 16 metatile ids ($E8AB, with the overlay structures over it), expand it to tiles and attributes (bank 5 $83B3), spawn the ground objects it holds ($89FB), arm the transfer ($A5 = 1) and set the new-row flag. Corridors has what the records say.
  • Art loader and spawn script ($E995, every frame): $E99F advances the art-load stream by one tile block when the previous one has decoded; $F78F runs the current wave script. Its waits are counted in new rows while the stage scrolls ($A0 bit 2 set by the row code: $68 goes down one per row) and in seconds ($69, reloaded with 60) when the scroll has stopped — so waves follow the scroll, and a boss that stops it gets a clock instead.

Sound

Two halves. Starting a sound is immediate and happens in the game code, in whatever step caused it: $D852 switches to bank 0, calls $8006 (which loads the song or effect header into a free soft channel) and switches back. Playing is the tick, once per frame at the end of the NMI (bank 0 $917C, about 1,600 cycles): it steps each active channel's duration, reads the next note or command from its stream, runs the pitch and volume envelopes, and writes the APU shadow $0308-$0317 to $4000-$4015. Notes therefore change on frame boundaries, never in between; a tick that finds $0307 non-zero does nothing. (Sound.)

The labyrinth's frame

The loop does not know which mode it is in. Everything above runs in the labyrinth too, in the same order: NMI, sync, pads, object loop, HUD, decompressor, boss routine, stage step, loader. What changes is what some of those steps find to do.

What is different

  • The stage step is almost empty. With $30 bit 6 clear, $E655 clears $B7 and the new-row flag, tests the stage-end flag ($A0 bit 0, which here means leave the room) and jumps straight to the loader: no scroll, no rows, no stream records, no ground objects. There is no E530 or E6AC in the trace.
  • The marker tile is not rewritten. The sprite-0 target is the room's own row 24 (Rendering), so the NMI skips that step ($30 bit 4 is clear).
  • Spawn-script waits are in seconds. There are no rows to count, so $F78F counts $69 down from 60 and takes one off the wait $68 each time: waits are in whole seconds.
  • Shots read the room. Every bullet and weapon looks up the cell under its hit box each frame (bank 6 $84E7) and may break it (Shooting the room); in a corridor that lookup always answers 0.

The player's step

The same slot-0 handler (bank 3 $8C98) takes the labyrinth branch at $8D03, once a frame:

  1. Facing and sprite ($8F53/$8F90): the D-pad cell $32 picks one of eight facings ($8EF4 → $0668); the facing and the animation frame $0638 choose the sprite's tile base ($8F13) and flip; after a hit the ship spins instead.
  2. Velocity: $F8CE turns the facing into a velocity at speed class $0698 = 3, 1.4 pixels a frame (a corridor's is 5, 2.3). Measured: x 124 → 139 in 11 frames holding Right.
  3. Move with the room's walls ($8FB9 far-calls bank 6 $826D): it forms the target position, offset 8 down to the ship's feet ($06B0), reads the classes of the cells it would touch from $0400, and if any blocks ($8425: classes 4-10 and 14) it snaps to the edge of the blocked cell and keeps the other axis moving, so the ship slides along walls: holding Down+Right against a wall it went on at 1.0 pixel a frame along it. Fractions are kept in $0758/$0770.
  4. What the cell under it is ($8FBF, only when the class $6C has changed since last frame): class 1 is the blue sphere (+20 chips, +2 life), class 2 the warp panel, which leaves the room if the key is held (Shooting the room).
  5. The room's edges ($9045): at y < 16, y ≥ 176, x < 14 or x ≥ 242 the ship is held at the edge — unless that exit is open ($54 bits 7, 4, 6, 5 for N, S, W, E) and has no key door ($58-$5B is 8), in which case it sets the exit direction $A4 (0 N, 2 W, 6 E, 8 S) and $A0 bit 0.
  6. Then the same as in a corridor: gun on B, weapon on A, hit flash ($8DF5 on).

Leaving a room: the loop stops

The exit flag is noticed at the top of the next loop pass, in $E655, which calls $EB18, and $EB18 does not return until the new room is on screen. In between, nothing of the normal frame runs: measured on the NES model, from the frame that took the exit to the first frame whose object loop ran again, the loop was suspended for 98 frames (east), 81 (north) and 81 (south). The pads are not read (so the player cannot steer), no object handler runs (enemies and shots vanish), the HUD and boss routine do not run; the transition's own code does the work, waiting with $FFD1 (a sync only) between steps, drawing the new room two tile rows a frame, moving the scroll, and drawing only the ship each frame ($F258: reset the allocator, the ship's sprite, finish). The NMI carries on: sprites, scroll, the sound tick. How the scroll itself works is on Rendering; the room is rebuilt from the ROM, which is why broken blocks come back.

The order, the cycle numbers, the slot order and the new-row share are from running the real code on the NES model (tools/tgl/cpu.py): the durations from five corridor savestates for 900 frames each (tools/profile-loop.py), the start-time timeline from the calm one for 400 (tools/trace-frame.py), the labyrinth frame from its savestate for 300, and the room-exit suspension from walking out of three exits ($30 bit 7 cleared; the ship's life held at its maximum so a run does not end); the routines' roles are from reading them. The NES model is not cycle-accurate (instruction timing is the table's, no DMA stalls, no IRQ, DMC or APU), so cycle numbers are indicative, and a stage with more enemies, a boss or heavier effects will take longer than the five states measured here. A one-off 6.5-frame stall (192,000 cycles in a single iteration, in a handler that was drawing a tile rectangle) appeared in an earlier run of more3 with a different life setting and did not come back; the routine that can do it is $D7C3, which makes any code that queues PPU data into a full queue spin until the NMI has drained it (a lead, not reproduced). Not established: the real hardware's frame budget; the sprite allocator's use of $81/$82 in the hiding loop; what every one of the 127 handlers does each frame (only the shared steps); the west exit's suspension (only east, north and south were timed); shops and message screens, which are special rooms with their own handlers; and the other uses of $FF8B with Y > 1.
