Graphics

This cartridge has CHR RAM, so not one byte of the file is a tile as stored. Everything the PPU draws was written there by code, and finding the writers is the whole problem.

The PPU write surface is closed and it is one queue. 31 STA $2007 sites and 18 STA $2006 sites in the whole file, all in bank 7, all traced — and a byte scan of the entire ROM finds exactly the same ones. An entry is [count][ppu_hi][ppu_lo][data], and the count byte's top two bits pick the type: under $80 a run with increment 1, $80-$BF the same with increment 32, $C0+ an attribute read-modify-write.

The tile codec

A block is a stream that toggles between two modes, and the toggle is a byte the block chooses for itself. A block begins [escape][unknown]. Decoding starts in literal mode, where every byte that is not the escape is one output byte. The escape switches into a run section, which is a sequence of [value][count] pairs; the escape switches back. Two escape bytes in a row — an empty section, in either mode — end the block. The compressor picks a byte that does not occur in the block's literal data, which is why the escape differs per block and why values like $A4 and $FD turn up alongside $01. The second header byte is always greater than the escape and is not understood; nothing in the decode uses it.

Three things check this, and they are independent. The partition: every block's decoded length ends exactly on the next pointer in its bank's table — 21 of 22 in bank 1, 29 of 29 in bank 2, 50 of 50 in bank 3. The terminator rule was worked out on four blocks and then predicted the other ninety-seven. The escape is forced: brute-forcing all 256 possible escape values against that test leaves exactly one survivor for 14 of bank 1's blocks, and it is header byte 1 every time. Hardware: decoding these blocks out of the ROM reproduces 398 of the 512 tiles of an in-game savestate's live CHR RAM, byte for byte, with 16 more blank.

The font: 45 glyphs, 1bpp, 7 bytes each graphics confirmed

bank2.font_8BF8 · bank 2 $8BF8-$8D32 · 315 bytes · codec font_1bpp_7byte

315 bytes = 45 x 7, and the seven is the whole point. This block is NOT tile-shaped and no graphics test that assumes 16 bytes per tile can see it - which is why this project's scan for a 1bpp font stored as 2bpp, sixteen consecutive tiles with an all-zero second bit plane, came back empty across the entire ROM. Playbook section 7 names this exact case: when a block will not divide by 16, ask what expands it before deciding it is not graphics. THE EXPANDER is bank 2 $806C. Per glyph it reserves a 19-byte queue entry, writes a count of $10 and the destination, then copies seven source bytes into data bytes 0-6, zeroes byte 7 at $8098, and zeroes bytes 8-15 through STA $010B,X - so the glyph occupies rows 0-6 of the low bit plane, row 7 is blank and the high plane is empty. It then advances the destination by $10 and the source by SEVEN, at $80AB. Every glyph therefore uses colour 1 only. CONFIRMED AGAINST THE HARDWARE: expanding the 41 glyphs this ROM's own record table uploads and comparing them with the live CHR RAM in a title-screen savestate gives 41 matches out of 41, byte for byte. The remaining four glyphs in the block are not uploaded by that table.

The title screen is not explained by any of this, and bank 0 has no table. The same hardware check against a title-screen savestate reproduces only 18 of 512 tiles. Those tiles live in bank 0, which holds tile-shaped data and no pointer table that passes the partition test — scanning every offset in bank 0 produced runaway decodes and a few unconfirmable candidates around $8BBB, nothing more. The code that runs the codec has also not been found. The decompressed bytes have to reach the $0100 queue, but no reader of these pointer tables has turned up in any scan run so far, and an absolute-indexed load from the table addresses finds nothing outside bank 4.
