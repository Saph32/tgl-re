Text

Three formats, not one, and they are not variations of each other. None of the text in this ROM sits in a block you could find by searching for it: the short strings are written inline after the JSR that prints them, the dialogue is behind a pointer table, and the screen layouts are reached through a pointer built from immediates that appears nowhere as an operand. All of it was found by following code.

Every punctuation glyph here is read from context, and the ROM cannot settle any of them. A font would, and there is no font: CHR is RAM on this cartridge, so no byte of this file is a tile until code uploads one, and no uploader has been found. The letters, digits and space are ASCII and need no argument. The rest are guesses with evidence, and the evidence is counted below.

The dialogue script

Twenty messages in bank 5, 2,263 bytes, the longest continuous prose in the ROM. $00 ends a message, $01 ends a screenful, $0D ends a line.

What carries this is not that it decodes. It is that the twenty messages partition $9639-$9F0F end to end with no gap and nothing over, and that every one of the 21 pointers lands on a message head. Those are two statements about the same bytes from two directions — the table and the terminators — and neither was derived from the other. A grammar whose lengths were all one short would still cover every byte.

The pointer table

Dialogue message pointer table pointer_table confirmed

bank5.msgtable_960F · file 0x1561F-0x15648 · 42 bytes · PRG bank 5 · CPU $960F-$9638

21 little-endian pointers, $960F-$9638, into the dialogue script that follows immediately. Read by bank 5 $8476: LDA $0620,X gives an object's message number, ASL A doubles it into Y, and LDA $960F,Y / LDA $9610,Y fetch the two halves - so the base in the operand is this region's own address, which is the strongest statement available that the table starts here. The entry count is bounded by structure, not by the reader: 21 x 2 = 42 bytes ends at $9639, exactly where the first message begins, with nothing over. NOTHING IN THE CODE BOUNDS IT - the index comes from $0620,X, an object field, and no CPY or mask on it has been found. Slots pointing at the same message: $9BC8 is named twice. That is in the data, not a parse error. Every one of the pointers lands on a message head, and the messages partition the block end to end - two statements from two directions, neither derived from the other.

Screen scripts

A different format for a different job — painting a whole screen rather than printing a sentence. An item is [col][count][characters], $FF ends a row and steps the PPU address on by $20, $FE ends the script, and bit 7 of the count repeats one character instead of advancing through the source. All of that is read off the renderer at bank 0 $8495, not inferred from the data.

The glyphs, and why each is only a lead

The three formats do not agree with each other, and that disagreement is the finding. The dialogue script uses $3C where a comma belongs; the bank 0 screen script uses $5C for the same job (LONG AGO,AN ALIEN RACE). An earlier entry in this project read $5C-$5F as a single 2×2 graphic from a bank 1 screen. All three readings cannot hold for one font — and they do not have to, because with CHR RAM the tile at a given index is whatever was uploaded last. Which is happening here is not established.
