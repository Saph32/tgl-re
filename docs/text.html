Text

Every string the code writes to the screen through the two inline-argument routines at $D576 and $D53F. These are not a block of text somewhere in the ROM: each one is written immediately after the JSR that prints it, so the bytes are scattered through the code of six banks and every one of them was found by the code trace rather than by searching for text.

The encoding is plain ASCII for A-Z, 0-9, space and a colon. Not by assumption: sixteen of these blocks read as English on a straight ASCII reading with no substitutions at all, which is more independent agreement than a coincidence can carry. The only codes outside that set anywhere in the payloads are $5B to $5F.
$5C-$5F are graphics, and $5B is a lead. Bank 1 writes $5C $5E to PPU $21AF and $5D $5F to $21CF — 32 bytes apart, one nametable row — so those four tiles are one symbol two tiles wide and two tall. That is layout, not resemblance. $5B is different: it sits just after Z and appears at the end of CONGRATULATIONS and twice in FR[ BA[ END, and a full stop fits all three. That is a guess from context and is recorded as one. The thing that would settle it is the font, and there is no font to look at — CHR is RAM here, so no tile exists in this file until code uploads it.

The count byte is the number of characters. A block is that count plus three when the routine is $D576, which carries its PPU address inline, and plus one when it is $D53F, which takes the address from RAM. Two blocks have bit 7 set in the count; it is masked off before the length is worked out, and what it means to the queue that consumes these is not established.
