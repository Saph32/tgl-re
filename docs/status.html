Status screen

Press Select during play: the world map, the seven keys, the twelve weapons, attack and shield, and a cursor to choose the weapon you fire.

How the game gets there

Bank 7 $E4B3 runs every frame of play. The controller routine $D626 shifts buttons in with ROL, so A lands in bit 7 and Right in bit 0; $D678 then keeps $F7/$F8 as held and $F5/$F6 as newly pressed. A new Start ($10) pauses; a new Select ($20), or Select during the pause, goes to $E4EE: sound $3E, bit 4 of $30 cleared, bank 5, JSR $801B → $84CB to open, then each frame JSR $8021 → $8937 until Start or Select is pressed, then JSR $801E → $8711 to close, bank 6 $8000, and the saved bank and $30 put back.
RoutineWhat it does
$84CBSaves the palette ($0181-$0198 → $04D0) and sprite 0's Y, then queues the whole screen: the map, twelve weapon icons to CHR $1800 and seven key icons to $1B00 through bank 2, the text, the stat bars and each slot's icon.
$8937Moves the weapon cursor $3C; bank 2 $8998 draws it and blinks the player's map position.
$8711Puts the palette back and, if the weapon changed, clears two object slots ($C048 with X = 3, 4) before returning to play.

The map

Bank 5 $8A6E, the same records the game walks while you move. $882D draws rows 0-23 as background tiles, each covering two by two cells; hardware sprites mark only the corridor entrances and (blinking) you.

Byte 1 of a cell is a key, and the picture shows it: $8860 tests byte 1 AND 7 against $04B0, and a cell whose key is not held is not drawn. The colours above come out in solid zones, not noise. Moving the cursor

$8937: a new press acts at once and sets a 20-frame delay, a held direction repeats every 6. Right adds 1 and Left subtracts 1, wrapping over 0-12; Down adds 5 and Up subtracts 5, wrapping within the columns. Position 0 is “no weapon” and 1-12 are the weapons, five to a row. After a move, $FD77 looks the weapon's level up into $3D, and a weapon at level 0 is skipped by moving again the same way — you cannot select what you do not have.

What a weapon costs

$FD77 reads $FDD3 + 3 × weapon + level into $45, the chips one use costs — the number printed after USE CHIP — and $3E = chips / $45 is how many uses you have left, drawn in the play HUD. The table's first byte read is $FDD7, straight after the 13-byte table at $FDCA, and its last is $FDF7, straight before code.

Regions

Item icons: 18 x 2x2 tiles, raw 2bpp graphics confirmed

bank2.gfx_8E0C · bank 2 $8E0C-$928B · 1,152 bytes

Eighteen 16x16 icons, 64 bytes each = four ordinary 2bpp tiles, stored UNCOMPRESSED. THE UPLOADER is bank 2 $81B2 (entry slot $8003): source = $8E0C + A * $40, queued as two 32-byte PPU writes to the CHR address in $18/$19. The four tiles are column-major - the status screen's $86F4 draws a selected icon as tiles $3C $3E over $3D $3F. THE EXTENT: the highest index any caller passes is 17 ($11, in bank 3's reward table $817A), and $8E0C + 18 * 64 is $928C, exactly where the next table - read by the other uploader - begins. Indices 0-11 are the twelve weapons: the status screen's $84CB uploads 0-11 to $1800-$1AFF (tiles $80-$AF) and $86ED uploads the selected one, index $3C - 1, to tile $3C. Indices 12-17 are non-weapon items, appearing only in the reward table. Rendered, all eighteen are recognisable framed pictures (docs/graphics.html). WHICH ICON IS WHICH WEAPON by name is not established from the ROM.

Key icons: the shared high bit plane graphics confirmed

bank2.gfx_928C · bank 2 $928C-$92AB · 32 bytes

The high bit planes of all eight key icons - one 2x2 frame every key shares. Bank 2 $8212 (entry slot $8006) builds each tile from 8 low-plane bytes out of the icon ($92AC + 32k) and 8 high-plane bytes from here: $928C,Y for tiles 0 and 2 and $9294,Y for tiles 1 and 3, with Y running 0-7 and then $10-$17. Those four reads cover $928C-$92AB exactly, 32 bytes. CORRECTION: tools/find-tables.py claimed $928C-$9293 as a bare 8-byte table; it is a quarter of this plane.

Key icons: 8 x 32 bytes of low bit plane graphics confirmed

bank2.gfx_92AC · bank 2 $92AC-$93AB · 256 bytes

Eight 16x16 icons stored as the LOW bit plane only, 32 bytes each (four tiles x 8 rows); the high plane is shared, at $928C. Uploader bank 2 $8212: source = $92AC + A * 32. Index 0 is an empty frame. THE EXTENT: callers pass 0-7 - bank 7 $ED51 passes $0058,Y AND $0F with 8 excluded, the status screen passes 1-7, and $F547 passes a per-area value from $F6DA - and $92AC + 8 * 32 is $93AC, where the unclaimed gap ends. Indices 1-7 are the SEVEN KEYS: $F547 ORs bit (k - 1) into $04B0 when key k is collected, and the status screen draws key k's icon only when that bit is set.

Item reward list: 73 x [threshold][icon] data confirmed

bank3.tbl_817A · bank 3 $817A-$820B · 146 bytes

73 two-byte records for the 'YOU GOT ITEM' screen. $80E7 walks them with X stepping by two and stops at CPX #$92 - so the table is 146 bytes, stated by the code - or at the first record whose threshold $817A,X exceeds $15. Each shown record prints its icon (the second byte, through bank 2 $8003) and its threshold as a decimal number (C051). CHECKS: the thresholds never decrease across all 73 (0 to 80), and every icon byte is 0-17, the range of the 18-icon table at bank 2 $8E0C. $15 is set by bank 6 $805A (far-called at $80D6): the TGL game's running score total at $04B3, in units of 10,000 displayed points, capped at 255 - so a threshold t means t0000 points, and the screen prints it that way ($802E appends the text 0000). $76, the list position, is kept between corridors, so every entry is given once per game. The screen exists only in the TGL corridors-only game ($ECF6, $30 bit 1); the icon goes to bank 2 $86BC, the pick-up routine. CORRECTION to the earlier text: 'what $15 counts is not established'.

Icon attribute by weapon level: 00 00 55 AA data confirmed

bank5.tbl_85DA · bank 5 $85DA-$85DD · 4 bytes

Read by $85C2 LDA $85DA,Y with Y = 0 or 1 for a key (held or not) and 0-3 for a weapon (its level from $C075), giving the attribute byte that picks the icon's palette: level 2 gets palette 1, level 3 palette 2. CORRECTION: the trace decoded $85DA as a BRK. It is never executed - the instruction before it is LDA #$20 / BNE, which always branches.

Status screen slot layout: 20 x [ppu lo][ppu hi][attr lo][tile] data confirmed

bank5.tbl_8690 · bank 5 $8690-$86DF · 80 bytes

Twenty 4-byte records, walked by $858B with Y stepping by 4 to CPY #$50. Slots 0-6 are the seven keys, on nametable row 0 from column 16 in steps of 2, tiles $B0-$C8; slot 7 is all zero and skipped by CPY #$1C; slots 8-19 are the twelve weapons in a grid at rows 14, 16 and 18, tiles $80-$AC. CHECKS: the tile numbers are exactly where the uploaders put the art ($1800 = tile $80, $1B00 = tile $B0), and every third byte is the correct attribute-table address for its slot's position, e.g. row 14 column 8 -> $DA.

Status map frame: 8 runs + $FF data confirmed

bank5.tbl_87E4 · bank 5 $87E4-$8804 · 33 bytes

Eight [count][ppu hi][ppu lo][tile] records and a $FF terminator, read by $8805 and each passed to C036 ($D5F8), which writes `tile` count AND $7F times - across, or down when bit 7 of the count is set. Two horizontal edges of 14, two vertical of 12 and four corners: the box around the 12 x 12-tile map.

World map: 24 x 24 rooms level confirmed

bank5.map_8A6E · bank 5 $8A6E-$91E9 · 1,916 bytes

576 variable-length records, 24 rows of 24 - one per room of the labyrinth. A record is (first byte AND $0F) + 1 bytes ($8103: LDA ($16),Y / AND #$0F / SEC / ADC $16). $80F5 seeks through it; $8071 walks it as the player moves ($52 column, $53 row); $882D draws it on the status screen as 2x2-cell background tiles, sprites marking corridor entrances only. BYTE 0: low nibble length-1, $80 exactly empty, bit 4 = layout pointer present, bits 5-6 = room kind ($5D; $20 and $40 carry a sub-id). BYTE 1: low three bits = the KEY that reveals the cell ($04B0), bit 3 = the room has enemies, bits 7/6/5/4 = openings north/west/east/south ($82DD against the neighbours $E0/$E2/$E6/$E8), and byte 0 bit 7 puts a key door in an opening. BYTE 2: bit 7 = corridor entrance, low seven bits = corridor number. THEN, in order: sub-id ($5E), spawn script id ($57, into $A4C7), layout pointer. CHECKS: 370 of 370 non-empty records are exactly as long as their flags imply; corridor numbers 1-21 occur once each; in the labyrinth savestate the live room pointer $E4 = $8E4C is this walk's row 12 column 8, and that room's layout and openings match the nametable cell for cell; 211 rooms with enemies use script ids 1-47, 47 distinct. CORRECTION: this region was first 807 records running to $960E, proved by 'the walk lands exactly on $960F' - a weak test that a walk over arbitrary data passes about one time in four. The map ends at $91EA, which $8042 names as the room-shape base. Generated by tools/parse-map.py.

Bit masks $01-$80 data confirmed

bank7.tbl_EFD8 · bank 7 $EFD8-$EFDF · 8 bytes

$EFC7 (C078) reads $EFD8,(A AND 7) for a mask and returns A >> 3 in Y as a byte index: the flag-array accessor behind $04B0 (keys), $04A9 (areas) and $04AC (weapon levels).

Per-selection value copied to $3B data confirmed

bank7.tbl_FDCA · bank 7 $FDCA-$FDD6 · 13 bytes

$FD77 does LDA $FDCA,Y / STA $3B with Y = the selected weapon $3C, 0-12: thirteen bytes. What $3B controls is NOT established.

Use-chip cost: 11 weapons x 3 levels data confirmed

bank7.tbl_FDD7 · bank 7 $FDD7-$FDF7 · 33 bytes

$FD77 computes Y = 3 * $3C + $3D and reads $FDD3,Y into $45, the chips one use costs - the number the status screen prints after 'USE CHIP'. $3C is 1-11 here (0 and 12 skip the read) and the level $3D is 1-3, so Y runs 4-36 and the bytes read are $FDD7-$FDF7: 33, ending exactly where the code at $FDF8 begins and starting exactly after the 13-byte table at $FDCA. Weapon 12 has no cost row - its count comes from $04AF instead. The costs rise steeply with level, e.g. 1, 3, 10 and 1, 5, 40.
